## 1. 目标与部署边界

移除 Redis 服务、redis/connect-redis/redlock 三个直接依赖及对应配置，使用项目自实现的有容量限制的内存模块，接管当前缓存、会话、短期状态、错误队列和互斥协调。

适用部署方式为 **一个 Vertex 实例运行一个 Node.js 业务进程**。当前仓库启动方式为单进程，可采用该方案。进程内存不跨进程共享，后续不能直接启用 Node cluster、PM2 多 worker、多副本或由 worker_threads 分别维护状态。粘性会话只能解决部分请求路由问题，不能提供共享任务状态和跨实例锁。

边界约定：

- SQLite、JSON 配置和 `/vertex` 持久化目录继续保留，业务历史不迁入内存。
- 不实现 Redis 协议、网络服务、分布式一致性或完整命令集合。
- 不新增其他缓存数据库，不将所有状态写回文件以模拟 Redis 持久化。
- 重启后缓存、登录会话、未完成的交互和短期标记清空，缓存按需重建；登录需要重新进行。现有会话签名密钥本就每次启动随机生成。
- 该方案与 Node.js 26 升级可分开实施和验收；若组合实施，应分别定位运行时兼容问题与状态管理问题。

## 2. 现有用途与替代策略

| 用途 | 当前位置及键 | 替代策略 |
| --- | --- | --- |
| HTML、RSS、JSON、POST 缓存 | `app/common/Site.js`、`app/common/Douban.js`、`app/libs/rss.js`、`app/libs/scrape.js` | 有字节及条目上限的 TTL/LRU 缓存 |
| 种子元信息 | `vertex:hash:*`，主要在 `app/libs/rss.js` | 可重建缓存；区分成功结果和失败结果的缓存时长 |
| SQLite 查询结果缓存 | `vertex:torrent:*`、`vertex:torrent_tracker:*`，位于 `app/common/Client.js` | 有上限的可重建缓存，未命中重新查询 SQLite |
| 抓取/刷新状态 | `vertex:scrape:free:*`、`vertex:douban:refresh_cache:*` | 独立 TTL 状态区；逐项确认业务语义，不与普通 LRU 混用 |
| 登录会话 | `app/routes/router.js` 中 connect-redis Store | 自实现 express-session Store，有独立容量、过期及注销规则 |
| 消息交互 | `vertex:select:*`，位于 `app/model/WebhookMod.js` | 有上限的交互状态区，保留 300 秒有效期，原子读取并消费 |
| 最近错误 | `app/libs/logger.js` 写入，`app/model/SettingMod.js` 读取并清空 | 同步定长队列，原子写入及 drain |
| 浏览器初始化锁 | `app/libs/redlock.js`、`app/libs/util.js` | 进程内互斥及浏览器生命周期管理 |

不能把所有键都当成可随时删除的缓存。例如 `vertex:scrape:free:*` 的存在与否会改变后续是否记录“非免费种”拒绝结果，提前淘汰会影响业务决策。此类标记应保持原有效期，容量不足时让相关操作以可重试状态退出，不静默丢弃。

交互键目前使用全局名称。实施时应按渠道和已验证的发送者/会话标识隔离，避免多个用户同时选择账号或媒体时相互覆盖；如果输入事件无法可靠识别用户，则明确限制为一个活动交互，第二个请求返回忙碌提示。

## 3. 模块划分

| 拟新增模块 | 职责 |
| --- | --- |
| `app/libs/memory/manager.js` | 全进程唯一实例、命名空间注册、总额度、统计和关闭 |
| `app/libs/memory/store.js` | Map 存储、TTL、字节核算、LRU、同步原子操作 |
| `app/libs/memory/cache.js` | 业务缓存 API、同键加载合并、前缀删除 |
| `app/libs/memory/session-store.js` | express-session Store 实现及请求生命周期协调 |
| `app/libs/memory/mutex.js` | 带等待队列上限与取消能力的进程内互斥 |
| `app/libs/memory/error-buffer.js` | 最近五条错误的有界环形队列 |

通过 CommonJS 模块缓存导出共享实例。底层内存模块不依赖业务 logger、util、数据库或路由，避免现有 logger → redis → logger 一类循环依赖。诊断通过计数器或限频 stderr 输出，不因记录错误而递归写入错误队列。

不直接启用 express-session 内置 MemoryStore；项目自行实现受控容量和清理机制。Express 官方明确说明默认 MemoryStore 不适合生产使用。

## 4. 内存与容量管理

建议首轮默认额度如下，实施后依据真实负载调整：

| 命名空间 | 估算数据额度 | 条目上限 | 达到上限的处理 |
| --- | --- | --- | --- |
| 普通可重建缓存 | 32 MiB | 30,000 | 先清过期，再淘汰 LRU；超大结果直接返回调用方但不缓存 |
| 登录会话 | 16 MiB | 2,000 | 清理过期会话；拒绝超额新会话，保留已有有效会话 |
| 影响业务决策的短期状态 | 8 MiB | 15,000 | 清理过期项；拒绝新增并向任务返回可重试错误 |
| 消息交互 | 4 MiB | 1,000 | 清理过期项；拒绝新交互并明确反馈 |
| 最近错误 | 1 MiB | 5 | 丢弃最旧错误，限制单条长度 |

全局估算数据上限初始为 64 MiB，并同时限制键长度、单条值长度。缓存单值建议最大 2 MiB，会话单值最大 64 KiB。所有数值必须通过统一配置解析，拒绝非有限值、负数和非法单位。

额度按存储后的键和值长度加固定元数据开销估算；使用字符串或 Buffer 存储边界，避免保留调用方可变对象引用。UTF-8 字节数并不等于 V8 堆大小，64 MiB 是模块的计账额度，不能声称是整个进程的实际内存硬上限。

在额度之外还要约束正在加载的数据、等待队列、会话活动请求和注销代次记录。观测 `process.memoryUsage()`、命中率、过期/淘汰次数、拒绝次数、加载中条目数与锁等待时间；压测时核对 heapUsed/RSS 是否稳定。浏览器内存也不计入该模块额度，容器总体内存需要另行预留。

## 5. 过期及 API 语义

### 5.1 基础语义

- 使用单调时钟计算进程内截止时间，通过可注入时钟完成测试；不要依赖系统时钟持续不回拨。
- 未命中或已过期返回 null；存储数字时按现有 Redis 字符串语义转换，例如 1 返回 `'1'`，保留当前 `+cache` 的行为。
- `set(key, value)` 覆盖旧值并移除旧 TTL；`setWithExpire(key, value, seconds)` 一次性完成写入和 TTL 设置。
- 有限的 TTL 必须为合法正整数秒；兼容 expire 的非正值立即删除语义，非法输入明确拒绝，不产生永久键。
- `expire` 不创建缺失键；过期续期、覆盖写入及字节计数在一次同步临界区中完成。
- 同步原子层内部不允许 await；保留异步兼容门面供现有调用方渐进切换，避免“单线程”被误认为多个 await 之间也具备原子性。
- `take` 原子读取并删除；错误队列 `drain` 原子取出并清空；`update` 使用同步更新函数，不允许返回 Promise。

当前 Redis 封装的 scan/deleteAll 未发现外部调用。实施时复核后删除未使用接口，业务如需批量删除则提供有限批次的 `deleteByPrefix`，不实现完整 SCAN/MATCH 协议。

### 5.2 清理策略

读取时立即检查 TTL，保证即使后台清理延迟也不返回过期值。后台使用一个带 `unref()` 的定时器，按有限条目及时间预算分批遍历清理，不为每个键创建一个定时器，也不在请求内全表扫描。

首轮可使用 Map 和分批游标，避免引入每次续期都追加节点的无界过期堆。需要长期保留的游标及迭代器必须周期性重建并验证引用释放；清理任务可在关闭时取消。

### 5.3 同键加载合并

增加 `getOrLoad(key, loader, options)`，同一键的并发未命中只发起一次抓取。独立限制加载中键数，失败时删除共享 Promise，不将异常永久缓存。缓存额度不足时允许返回成功抓取结果；涉及业务状态的额度不足必须使用不同的错误类型，避免被现有通用抓取异常路径误写为永久拒绝记录。

鉴权上下文相关的缓存键包含方法、规范化 URL、必要请求体摘要及身份摘要，不能只按 URL 在不同账号间复用。摘要或原始键也不应直接写入公开日志。

检查 `Site._getDocument` 在命中/未命中、retCookies 参数下的返回形状；需要新的 Set-Cookie 时绕过 HTML 缓存。更换存储不能导致相同接口在不同路径返回不同结构。

## 6. 登录会话

自定义 Store 继承 `express-session.Store`，实现 get、set、destroy 和 touch；按官方要求调用回调，确保每次恰好回调一次。回调统一异步派发，防止同步/异步行为混杂。可补充 clear 和 length，但不暴露会话内容列表作为诊断接口。

具体规则：

- 保留 `resave: false`、`rolling: true`、`saveUninitialized: false`、30 天 cookie 有效期和现有 cookie 属性。
- get 返回序列化快照的独立副本，防止一个请求直接修改其他请求正在使用的对象；不得把 Set、Map 等不可稳定序列化内容放入会话。
- 根据 cookie 剩余有效期生成内存 TTL，touch 只延长仍存在且有效的会话，绝不创建缺失会话或恢复已注销会话。
- destroy 删除会话并推进注销代次。增加请求级代次校验，拒绝同 SID 已开始请求在注销后迟到保存的旧会话；代次记录至少保留至相关活动请求结束，活动请求及相关元数据都需要数量和时限约束。
- 对同 SID 的读改写竞争增加明确的保存次序或版本校验。注销/再生成之后的过时保存必须失效，不能依靠简单 Map.set 覆盖来处理。
- 超过容量时新登录明确失败，不能先返回登录成功、随后因写入失败立即掉线；触发点需覆盖 express-session 保存回调。
- 进程重启后重新登录，不将会话写入 JSON 或缓存快照文件。

会话容量规则和错误处理必须通过真实 HTTP 集成测试验证，不能仅测试 Map 的增删改查。

## 7. 锁与浏览器生命周期

当前 Redlock 仅用于保护浏览器初始化，锁期限 15 秒；调用方释放锁后还会创建页面、抓取内容及按页面数量关闭浏览器。替换时需要同时处理这些生命周期竞争。

- 实现 `runExclusive(resource, task, { waitTimeoutMs, signal })`，FIFO 等待队列有上限。
- 锁拥有者在 finally 中释放；使用拥有者标识防止重复释放、迟到释放解开其他持有者的锁。
- 等待超时或 AbortSignal 取消时移除等待者。不要用 TTL 到期后自动放行来“解锁”仍在执行的浏览器初始化，否则会同时启动多个浏览器。
- 浏览器初始化通过共享初始化 Promise 合并，同一时刻只初始化一次；失败后清除该 Promise，允许重试。
- 用活动任务计数和生命周期互斥协调创建页面与关闭浏览器，不能仅凭 `browser.pages().length` 判断可关闭。
- 等待超时不等于持有者任务取消；持有者依赖独立的浏览器启动/抓取超时，完成清理后才能释放资源。关闭程序时停止接受任务、取消排队并清理浏览器。

确认没有外部调用后移除 `util.redlock` 导出及 `app/libs/redlock.js`，不保留名为分布式锁的内存实现。

## 8. 错误队列与业务标记

错误记录使用同步环形队列，最多五条且有单条字节上限。logger 写入与 SettingMod 读取清空通过单个原子 drain 协调，避免现有 get → 修改 → set 与读取清空并发导致丢失记录。错误序列化失败也不能递归调用业务 logger。

种子存在性和 tracker 查询缓存可由 SQLite 重建，淘汰后允许再次查询；检查新增、删除等写操作是否需要主动失效缓存。

抓取等待、刷新限频等标记按当前 TTL 保留，独立于可重建缓存。无 TTL 的键逐一分类：可以重建的使用有界缓存；不能丢失的业务事实回到 SQLite 或现有配置数据中表达，不创建无限增长的永久 Map。

种子元信息抓取失败形成的占位结果应区分为短期负缓存，避免一次异常在整个运行期持续阻止重试；具体时长通过请求量和业务测试确认。

## 9. 改动清单与实施顺序

1. **新增内存模块及测试。** 固定返回值、TTL、容量与错误约定；以可注入时钟和加载器测试并发及过期。
2. **替换可重建缓存。** 将 Site、Douban、rss、scrape、Client 的对应缓存调用改为内存模块。保留各调用处现有业务 TTL，分开迁移决策状态。
3. **替换错误、交互和业务状态。** 使用原子 drain/take，按发送者隔离交互；容量不足走可重试处理，而非错误的业务拒绝分支。
4. **替换会话及锁。** routes 使用自定义 Store，浏览器使用进程内管理器；通过登录、注销和并发抓取测试。
5. **移除 Redis 代码与依赖。** 删除 `app/libs/redis.js`、`app/libs/redlock.js`、RedisStore 和所有客户端创建；移除 package.json 的 redis/connect-redis/redlock 并更新锁文件。
6. **移除配置和日志残留。** 删除 config.getRedisConfig、配置模板的 redis 项、REDISPORT；将 logger.yaml 的 `%x{redis}` token 及 logger 对应 token 名同步更名，保留日志格式可用性。纯 Redis 模板清空后需检查读取方，而非盲目删除整个配置加载链。
7. **移除容器依赖。** 从基础镜像 Dockerfile 删除 redis 包，如后续新增了 Redis 配置或检查也同步删除；从应用 Dockerfile 删除 Redis 配置步骤；从 start.sh 删除 Redis 环境变量和启动命令。不要误删与 Node/Chromium 仍有关的步骤。
8. **更新开发环境和 CI。** 启动后端无需 Redis，增加内存单元测试和真实会话/浏览器集成测试，确认 Node.js 26 升级方案中的 Redis 验收项已被新的状态管理验收替代。

可分批提交，但发布包含完整实现的一组变更；不用旧客户端连接已删除的服务。最终不保留生产 Redis 开关、并行双写或暗中回退 Redis 的路径。

## 10. 与基础镜像升级的关系

现有 [`docker/vertex-base/Dockerfile`](../../docker/vertex-base/Dockerfile) 是保留 Redis 的 Node.js 26 / Alpine 方案，仍供当前应用适配使用；本次仅补充文档，没有修改该文件。

如果决定同时实施本方案，待应用完成替代后，再从基础镜像删除 Redis 相关内容，发布独立标签，例如 `lswl/vertex-base:node26.13.0-alpine3.24-no-redis`。应用 Dockerfile 的两个阶段同时切换该标签或索引 digest，避免提前覆盖仍被旧应用使用的基础镜像。

基于已有镜像再执行 apk del 不能移除旧镜像层，最终应从不安装 Redis 的 Dockerfile 重新构建。

## 11. 验收清单

| 类别 | 必测场景与通过条件 |
| --- | --- |
| TTL | 过期边界、续期、覆盖后清除 TTL、非法值、长会话、系统时间变化；过期内容始终不可读 |
| 容量 | 超大内容、超长键、大量唯一 URL、不同命名空间争抢额度；已有会话和业务状态不被普通缓存淘汰 |
| 并发缓存 | 同键多请求仅加载一次；失败后可重试；删除/失效与正在加载的请求竞争有明确定义，不让旧结果重新覆盖新值 |
| 原子消费 | 并发交互仅消费一次；错误并发写入与 drain 不重复、不丢失已完成写入的记录 |
| 会话 | 登录、刷新、滑动过期、注销、再生成、并发迟到保存、容量拒绝、重启重新登录 |
| 业务决策 | 抓取等待标记不因 LRU 压力消失；内存拒绝不会被误记为永久业务拒绝 |
| 互斥 | FIFO、队列满、等待超时、取消、异常释放、重复释放；不会同时初始化浏览器或关闭仍被使用的浏览器 |
| 长期运行 | 大量过期与续期后条目、定时器、加载中 Promise、锁队列等不持续增长，heapUsed/RSS 无持续上升趋势 |
| 无 Redis 部署 | 在没有 Redis 可执行文件、没有 6379 监听的环境启动并运行；代码不再尝试连接 Redis |
| 双架构 | amd64/arm64 应用镜像均通过核心集成测试 |

基准场景和阈值在实施时先记录，再对比替换结果；不预先承诺一定降低整个应用的 RSS，因为原 Redis 内存将转入 Node 堆，GC 行为也会变化。
